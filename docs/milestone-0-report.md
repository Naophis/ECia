|---|---|---|---|
| HSA | PA8 | TIM1_CH1 | 6 |
| LSA | PA7 | TIM1_CH1N | 6 |
| HSB | PA9 | TIM1_CH2 | 6 |
| LSB | PB0 | TIM1_CH2N | 6 |
| HSC | PA10 | TIM1_CH3 | 6 |
| LSC | PF0 | TIM1_CH3N | 6 |
| BEMF_A | PA0 | COMP1_INM (IO2), ADC1_IN1 | — |
| BEMF_B | PA4 | COMP1_INM (IO1), ADC2_IN17 | — |
| BEMF_C | PA5 | COMP2_INM (IO1), ADC2_IN13 | — |
| BEMF_N | PA1 | COMP1_INP (IO1), ADC1_IN2 | — |
| BEMF_N | PA3 | COMP2_INP (IO2), ADC1_IN4 | — |
| PWM1 | PA2 | TIM15_CH1 | 9 |

**No contradiction was found between the schematic and the MCU.** Every pin the
schematic assigns supports exactly that function, and the comparator plan in
the spec (§7) is not just workable — it is the only one this package allows.

Three findings worth calling out:

1. **The BEMF_N double connection is explained and must stay.** PA1 is the only
   COMP1_INP available on UFQFPN32 (the alternative, PB1, is not bonded out),
   and PA3 is the only usable COMP2_INP (the alternative, PA7, is TIM1_CH1N
   here). Each comparator needs its own wire to the virtual neutral.
2. **Hardware blanking is available.** `COMP_CSR.BLANKING = 0b001` selects
   TIM1_OC5 for both COMP1 and COMP2, so the post-commutation blanking window
   of spec §11 can be generated by the same timer that makes the PWM, with no
   software in the path.
3. **No current or voltage sense reaches the MCU.** PA6 and PF1 are
   unconnected. As spec §14 already anticipates: no phase-current control, no
   software current limit, no low-voltage cutoff. The only current limit on the
   bench is the physical supply limit, and MP6540HA's internal protection must
   not be treated as a regulator.

The gate driver is the **MP6540HA** (six independent HS/LS inputs), confirmed
by hardware test on this board, not by the schematic symbol — which is a reused
MP6540H symbol with ENx/PWMx pin names. The MCU generates the dead time.

### Silicon, read from this board

`./tools/hilctl identify --json`:

```json
{"connected": true, "mcu": "STM32G431xB", "idcode": "0x20036468",
 "dev_id": "0x468", "rev_id": "0x2003", "flash_size_kb": 128,
 "package_raw": 8, "uid": "3031383930364B10002C0009",
 "probe_serial": "37FF71064E57343677A31A43", "core_state": "running"}
```

DEV_ID `0x468` = STM32G431/G441; 128 KiB flash selects the `xB` member. Package
and temperature grade are not readable from silicon, so the adapters claim only
`STM32G431xB`; UFQFPN32 is corroborated by the board using PF0, which only the
32-pin package bonds out.

### Clock tree

170 MHz maximum. **There is no crystal** — PF0/PF1 are the OSC pins and PF0 is
TIM1_CH3N — so HSI16 + PLL is the only option. Observed live on the board now:
`RCC_CR = 0x03000500` (HSI on and ready, PLL on and ready), `RCC_CFGR = 0xF`
(SW = SWS = PLL). `RCC_CSR = 0x1C000000` — PIN + BOR + **SFT** reset flags, i.e.
the last reset was a software/debugger reset left by an earlier session.

### Current bridge state on the board (read-only, no writes)

`RCC_APB2ENR = 0`, and TIM1 `CR1` / `CCER` / `BDTR` / `CNT` / `ARR` / `CCMR1`
all read `0x00000000`. **TIM1 is not even clocked, so nothing is driving the
gates.** Whatever firmware is resident is not ESCape32 (which enables
SYSCFG/TIM1/USART1 on APB2) and is idle with respect to the power stage.

## B. Timer design

```
COMP1/COMP2 ──(TIM2_TISEL)──▶ TIM2_TI1 ──▶ IC1 capture  = ZC timestamp (hardware)
                                                │
                                      T60 filter, +T60/2
                                                ▼
                                          TIM2_CCR3 ──▶ OC3REF ──▶ TIM2 TRGO
                                                                      │
                                                          TIM1 TRGI (ITR1)
                                                                      ▼
                                                        TIM1 COM event
                                                   (CCER/CCMR preloaded state
                                                    for all three phases applied
                                                    in one hardware update)
TIM1_OC5 (CCR5) ──▶ COMP_CSR.BLANKING = TIM1_OC5  = post-commutation blanking
```

**TIM1 — bridge only.** 170 MHz, edge-aligned up-counting PWM mode 1,
`ARR = 170e6 / f_pwm − 1` with `f_pwm` a configuration value in the 24–48 kHz
band (32 kHz → ARR 5311). `CCMRx.OCxPE` and `CR1.ARPE` set so duty and period
change only on update. `CR2.CCPC = 1` and `CR2.CCUS = 1` so the channel-enable
bits are preloaded and applied **on a COM event triggered from TIM2's TRGO**,
never by writing GPIO in sequence and never from the PWM ISR. Dead time in
`BDTR.DTG`: the 548 ns measured on this board with the same MP6540HA is 93
ticks at 170 MHz (`DTG = 0x5D`), measured for real in Milestone 1 by the
on-chip gate capture.
`BDTR.OSSI = OSSR = 1` with all `OISx = OISxN = 0`, so clearing `MOE` drives all
six gate inputs **low** rather than releasing them to float; the six GPIOs also
get internal pull-downs to cover the window between reset and TIM1 init. TIM1
channel 5 is internal-only and drives the comparator blanking window.

**TIM2 — timing, 32-bit, free-running at 170 MHz.** One tick is 5.9 ns and it
wraps in 25 s; a 100 krpm sector is 14.3 µs = 2431 ticks, so resolution is not a
constraint. CH1 input capture, its input selected by `TIM2_TISEL` between
COMP1_OUT and COMP2_OUT, hardware-timestamps every zero crossing with no ISR
latency; the input filter `IC1F` rejects switching noise on top of the COMP
blanking. CH3 output compare produces `OC3REF` → TRGO → TIM1 COM, so the
scheduled commutation at `zc + T60/2` happens in hardware while the CPU only
computes the next compare value. This is spec §12's "dedicated timing timer"
with the CPU fully out of the jitter path.

**COMP1 / COMP2 — one active at a time**, mux switched per sector to the three
configurations in [hardware-mapping.md](hardware-mapping.md), with
`COMP_CSR.POLARITY` normalising the expected edge so software always looks for
the same polarity.

**TIM6 (or SysTick) — 1 kHz housekeeping** for state-machine timeouts, the
`duration_ms` limit and the debug ring drain. Never in the commutation path.

**IWDG** refreshed only from the main loop, so a stalled control loop stops the
bridge without the host.

Interrupt priority: TIM2 CC1 (zero cross) highest, then TIM1 COM/UPD, then
everything else. PWM frequency and commutation frequency stay independent, as
spec §9 requires.

## D. Difference from this design

Everything in section B is new work; there is no existing implementation to
diff against. The meaningful deltas are against the two reference firmwares
that have run on this board:

| Topic | ESCape32 / AM32 on this board | This design |
|---|---|---|
| Scope | General ESC frameworks (configurator, telemetry, DShot, bidirectional, EEPROM, bootloader) | One fixed path: forced 6-step → COMP ZC → sensorless 6-step. Nothing else. |

| Startup | ESCape32 has no blind ramp (this is why it stalled here); AM32 has one | Explicit ALIGN → forced commutation → ramp → acquire, all parameterised |

## E. Milestone 1 implementation plan

**In scope: TIM1 only. No COMP, no BEMF logic, no motor connected.** Spec §19
Milestone 1 asks for PWM, dead time, Hi-Z and sector transition to be
confirmed. It assumes an oscilloscope; there is none on this bench, so the
measurement is made on-chip instead (below).

Files to create (none exist yet):

```
CMakeLists.txt                 cmake/arm-none-eabi.cmake     ld/stm32g431kb.ld
vendor/cmsis_core/             vendor/cmsis_device_g4/       (pinned, vendored)
src/startup_stm32g431.c        src/clock.c                   src/main.c
src/motor_hw.c        include/motor_hw.h        TIM1 + TIM2 setup
src/motor_commutation.c include/motor_commutation.h  sector table, preloaded bridge state
src/motor_control.c   include/motor_control.h   state machine + duty
src/motor_debug.c     include/motor_debug.h     debug GPIO + event ring
src/hil.c             include/hil.h             hil_cmd / hil_state (docs/hil-abi.md)
```

Toolchain: `arm-none-eabi-gcc 13.2.1` (present), CMake 3.28 (present). **CMSIS
device headers, no HAL** — the spec allows HAL for init but prefers LL/direct
register access for anything time-critical, and the whole of Milestone 1 is
time-critical. Vendoring `stm32g431xx.h` and CMSIS-Core keeps every register
definition authoritative *and* the build offline-reproducible. Artifact:
`build/ecia_bldc.elf`, linked at `0x08000000`, with the short git SHA compiled
in as `hil_state.build_id`.

Milestone 1 behaviour: `request = run` configures TIM1 for the requested duty,
holds sector 0, then steps sectors 0→5 at a configurable fixed period, and
returns to `STOP` with `MOE` cleared after `duration_ms`. No BEMF, no COMP, no
closed loop.

How it will be checked — **there is no oscilloscope on this bench**, so the
measurement moves into the MCU. Full design in
[on-chip-capture.md](on-chip-capture.md).

1. **On-chip gate capture, every trial.** TIM7 triggers a DMA stream from
   `GPIOA_IDR` into an 8 KiB SRAM buffer at 17 MHz (58.8 ns per sample, 241 us
   ≈ 7.7 PWM periods). `IDR` reflects the actual pin, so this is the real
   waveform at the MP6540HA gate inputs: PA8 = HSA, PA7 = LSA, PA9 = HSB,
   PA10 = HSC. The host reads the buffer back over SWD into
   `.hil/logs/<trial_id>/`. From one capture:
   - **PWM** — period and duty of HSA, expected within 1 % / one sample.
   - **Dead time** — run length with HSA and LSA both low, at every transition
     in both directions. The sample clock is deliberately incommensurate with
     the PWM period (531.2 samples per period), so the sampling phase slides
     and the run-length histogram recovers the width to well under one sample.
   - **No shoot-through** — `HSA AND LSA` must be zero across the whole
     capture. Absolute, not statistical.
   - **Hi-Z** — the floating phase's two gates low for the entire sector.
   - **Sector transition** — the six patterns in order, all three phases
     changing within one sample at the COM event, i.e. commutation is atomic.
   A second change later adds two more DMA channels on the same TIM7 request
   for `GPIOB_IDR` (PB0 = LSB) and `GPIOF_IDR` (PF0 = LSC).
2. **Register readback over SWD, every trial** — `BDTR` (`MOE`, `DTG`),
   `CCER`/`CCMR1..3` per sector, `ARR`/`CCRx`, TIM1 `CNT` advancing,
   `hil_state.sector` stepping. Cross-checks the capture against what was
   actually configured.
3. **BEMF dividers via ADC, as a later change in the same milestone** — an ADC
   burst on PA0/PA4/PA5 with a held sector confirms the *power stage* follows
   the gates, not just the MCU pins: source phase peak ≈ VIN·10/66, sink ≈ 0,
   floating apart from both. The peak also **measures VIN**, which nothing else
   here can observe.

What this still cannot see: the MP6540HA's own propagation delay and the phase
node's switching edges. Two datasheet facts make that acceptable —
`HSx = LSx = H` yields high impedance rather than shoot-through, and no
propagation delay is specified at all, only 0.33 V/ns slew (~38 ns at 12.6 V)
against a ~550 ns dead time. Milestone 1 is therefore complete on measured
evidence, with that limitation recorded rather than assumed away.

First trial: `--duty 5 --duration-ms 200 --rpm-limit 0`, motor disconnected,
sector held, gate capture only. Sector stepping is the second trial.

Before the first trial the firmware is built locally with
`python3 tools/hil-adapters/build.py` — a build failure inside `hilctl trial`
ends the campaign and costs a re-arm, so the build is made to succeed first.

### Results

- `python3 -m unittest discover -s tests` — **52/52 pass**: the kit's own 28 (8
  of which could not run before the hooks were reconstructed), plus 24 new ones
  covering the gate-capture analysis and its readback path.
- `.hil/config.json` — validated against `hilctl`'s own `doctor` rules
  (placeholder binding, no shell interpreter, no post-flash run, flash range
  `0x08000000`–`0x08020000`): **no issues**.
- `./tools/hilctl identify --json` — **ok**, output in section A. 170 ms.
- `./tools/hilctl stop` — **stopped**, off-state confirmed
  (`BDTR`/`CCER`/`CR1` all `0`, core halted). 257 ms.

### Why the stop path looks the way it does

Halting the Cortex-M does **not** stop TIM1: with the core halted the timer
keeps PWMing whatever sector was active, so one phase stays energised. Freezing
TIM1 via `DBGMCU_APB2FZ.DBG_TIM1_STOP` (`0xE0042010` bit 11) is not a fix
either — the outputs freeze at their instantaneous level, which can be a
permanently-on high side. Clearing `MOE` is the only primitive that actually
releases the gates, so it is the first thing `stop.py` does after halting.
Corollary for every powered milestone: **never set a breakpoint inside an
energised run.**

## G. Open risks and what is still needed

1. **`.hil/safety-policy.json` does not exist and I must not create it.**
   CLAUDE.md makes the safety ceiling user-owned. A template with
   Milestone-1-appropriate values sits at `.hil/safety-policy.template.json`
   (10 % duty, 2000 ms, 1000 rpm, 20 trials, 3 repeats). `doctor` cannot return
   `ok` until it is in place; that is the first half of the command in the
   handover.
2. **No oscilloscope.** Resolved by the on-chip gate capture
   ([on-chip-capture.md](on-chip-capture.md)), which measures dead time,
   duty, Hi-Z, sector atomicity and shoot-through at the MCU pins. The residual
   gap — the gate driver's own propagation delay and the phase-node edges — is
   bounded by the datasheet, not measured. Recorded, not assumed away.
3. **VIN and the motor connection are not observable until the ADC step.**
   Milestone 1 requires **the motor disconnected** with VIN applied. 3V3 is
   clearly present (SWD works, and per the board notes 3V3 comes from an
   LMZM23600 off VIN), so VIN is probably applied — but that stays an inference
   until the ADC burst measures the source-phase peak.
4. **Automatic synchronous rectification defeats a truly floating phase.** The
   MP6540HA turns its LS-FET on by itself whenever an off phase is driven below
   ground, until that current reaches ~zero. Spec §8 requires the floating
   phase to be genuinely Hi-Z during zero-cross detection, so from Milestone 3
   the blanking window must outlast the recirculation, not just the switching
   noise. This is a plausible contributor to the sync failures the ESCape32
   build had on this board, and it is the first thing to instrument in
   Milestone 3.
5. **Resident firmware is unknown.** Something is running with the PLL up and
   APB2 clocks off. It is not driving TIM1, and Milestone 1 will overwrite it.
6. **Dead-time value is inherited, not yet measured on this MCU.** 93 ticks
   @170 MHz comes from 548 ns measured with the same driver at 168 MHz. It is a
   starting value, and Milestone 1's first trial measures the real one.
7. **The MP6540HA gate inputs during the reset window are safe.** Previously an
   open risk; the datasheet states the logic inputs have weak internal
   pull-downs, so the pins floating between reset and TIM1 init leave all
   outputs high-impedance. Firmware still adds GPIO pull-downs and uses
   `OSSI = 1` with `OISx = 0`.
8. **No current measurement of any kind reaches the MCU.** The bench supply's
   current limit is the only real current protection; MP6540HA's OCP sits at
   10-17 A, far above anything this motor should draw.
